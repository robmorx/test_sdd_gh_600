# CLI Contract Checklist: DevLog CLI

**Purpose**: Requirements-quality review of the command-line contract of DevLog CLI — the command surface, its input rules, its user-facing messages, its exit codes and the flows it must cover. It tests whether these requirements are *written well*, not whether the tool behaves correctly.
**Created**: 2026-10-21
**Feature**: [spec.md](../spec.md) · [contracts/cli.md](../contracts/cli.md) · [Clarifications](../spec.md#clarifications)

**Scope of this review**: `spec.md` (including its `## Clarifications` section) and `contracts/cli.md`. General spec quality (measurable success criteria, acceptance-criteria coverage in general) is already covered by the built-in `requirements.md` checklist and is not repeated here.

**Note**: This custom checklist is generated by the `/speckit.checklist` command based on feature context and requirements.
**Review Ownership**: This checklist is a reviewer-owned requirements-quality review artifact. Mark an item `[x]` only when the reviewer determines the requirements-quality criterion is satisfied.
**Marker Semantics**: `[x]` means the criterion has been reviewed and satisfied for requirements quality. It does not mean implementation work is complete.

## Requirement Completeness

- [x] CHK001 Are all four command surfaces (`add`, `list`, `search`, `export`) specified with their arguments and options, including the alternative title and content input paths? [Completeness, Spec §FR-001..FR-014]
- [ ] CHK002 Are the input sources for a note's body exhaustively specified — inline content, content file, standard input — with the precedence between them stated? [Completeness, Spec §FR-001, Contract §2] — **Finding**: the contract defines the fallback to standard input ("if neither `--content` nor `--content-file` is given"), but never states which one wins when **both** `--content` and `--content-file` are supplied. The rule is unstated, so the requirement is not complete.
- [x] CHK003 Are the tag input rules specified for both a repeated flag and comma-separated values inside a single flag? [Completeness, Spec §FR-017, Contract §2]
- [x] CHK004 Is the title requirement — mandatory, not empty, not whitespace-only — stated once and referenced consistently by every requirement that depends on it? [Completeness, Spec §FR-016]
- [x] CHK005 Are the output requirements for each command specified, including which stream each message goes to and which fields a result line carries? [Completeness, Contract §2-§5]
- [ ] CHK006 Are the help-text requirements defined, or is the generated help left entirely to the implementation? [Gap, Contract §1] — **Finding**: only the `--help` flag itself appears in the contract; no requirement states what the help text must contain, nor which arguments or examples it must document. The language row scopes the help text to Spanish but not its content.

## Requirement Clarity

- [x] CHK007 Is "explicit user confirmation at that moment" defined concretely enough to distinguish an interactive prompt, an explicit flag and a non-interactive session? [Clarity, Spec §FR-015, Clarifications §Session 2026-10-21]
- [x] CHK008 Is the exit-code contract stated as a complete enumeration (0 / 1 / 2 / 3) with the exact condition attached to each code? [Clarity, Spec §FR-021, Contract §1]
- [ ] CHK009 Is the interface-language requirement scoped precisely enough to know which artifacts it covers — help text, confirmations, error messages, exported document? [Clarity, Spec §Assumptions "Interface language", Gap] — **Finding**: the requirement exists only as an assumption in the spec, never as a functional requirement. The contract scopes it to "help text, confirmations, warnings, and errors", and says nothing about the exported Markdown document, whose headings and metadata labels are in Spanish by implementation but not by requirement.
- [x] CHK010 Is the listing line format specified precisely enough that two independent implementers would produce the same output? [Clarity, Spec §FR-008, Clarifications §Session 2026-10-21]
- [ ] CHK011 Are the terms used for "title", "content" and the search result set defined once and used consistently, including whether surrounding whitespace in the title is significant? [Clarity, Spec §FR-001, FR-010, FR-011, FR-016] — **Finding**: the spec normalises **tags** (trim, lowercase) but never states whether surrounding whitespace in a **title** is preserved or trimmed. The two documents are consistent with each other but both silent, so the title's whitespace handling is undefined.

## Requirement Consistency

- [x] CHK012 Are the store-location requirements identical in the spec, the Clarifications section and the contract, including the environment-variable override? [Consistency, Spec §FR-003, Clarifications §Session 2026-10-21, Contract §1]
- [x] CHK013 Do the exit codes in the contract match the codes required by FR-021 and the codes assumed by the Quickstart scenarios? [Consistency, Spec §FR-021, Contract §1, Quickstart §3-§7]
- [ ] CHK014 Do the error-message requirements in FR-020 align with the exact Spanish wording fixed in the contract, or is the wording left to implementation discretion? [Consistency, Spec §FR-020, Contract §2-§5] — **Finding**: the two do not conflict, but their **hierarchy is unstated**. FR-020 asks for "understandable" messages without fixing the wording, while the contract fixes exact strings; no requirement says the contract wording is normative, so an implementer reading only the spec would have discretion over the text.
- [ ] CHK015 Is the "every requested tag" rule stated consistently across FR-010, the User Story 3 acceptance scenarios and the contract? [Consistency, Spec §FR-010, Spec §User Story 3, Contract §4] — **Finding**: FR-010 and the contract both state the AND rule, but the three User Story 3 scenarios only exercise a **single** tag. No acceptance scenario covers multiple tags, so the most subtle rule in the feature has no acceptance coverage.
- [x] CHK016 Are the requirements for replacing an existing export file stated consistently in FR-015 and in the contract, including the non-interactive refusal? [Consistency, Spec §FR-015, Contract §5]

## Acceptance Criteria Quality

- [x] CHK017 Can the "no results" outcome be objectively verified from the requirements alone, without needing to know the exit-code table? [Acceptance Criteria, Spec §FR-011, FR-021]
- [ ] CHK018 Is the criterion for the confirmation flow (a declined overwrite leaves the existing file untouched) stated as a verifiable outcome rather than an expectation? [Acceptance Criteria, Spec §FR-015, Contract §5] — **Finding**: US4 scenario 2 verifies that the tool *asks* before replacing, but the **declined** outcome (file untouched, exit code 1) is specified only in the contract, not in any acceptance scenario of the spec.

- [x] CHK026 Are boundary requirements defined for tags that repeat, differ only in case, or arrive with surrounding whitespace? [Edge Case, Spec §FR-017, Contract §2]

## Ambiguities, Conflicts & Traceability

- [ ] CHK028 Is there an established identifier scheme linking every requirement to its acceptance scenario and to the contract section that governs it? [Traceability] — **Finding**: partial only. The contract carries a per-command "Acceptance coverage" line naming the FRs and scenarios it covers, but there is no complete FR → acceptance scenario → contract section mapping, and several FRs (FR-005, FR-006, FR-011) are not cited by any contract section.
- [x] CHK029 Are the requirements refined during planning — default export path, listing format, exit codes — explicitly ratified in the requirement text, or do they live only in the clarification log? [Traceability, Clarifications §Session 2026-10-21]
- [x] CHK030 Do any requirements rely on vague qualifiers — "readable", "understandable", "clear" — that are not tied to a measurable criterion or to an exact message? [Ambiguity, Spec §FR-013, FR-020]
- [ ] CHK031 Are the assumptions that carry product decisions (single actor, offline, no categories, Spanish interface) each traceable to a requirement, so that a change to one forces a change to the other? [Assumption, Spec §Assumptions] — **Finding**: all assumptions map to a functional requirement except **interface language**, which has no FR of its own (see CHK009). A change to that assumption currently forces no change to the requirement set.
